# 约束：权限与审批

> 本文是 [AGENTS.md](../../AGENTS.md) 的 L1 分域约束：**改权限判定、审批通道、只读白名单前必读**。
> 面向使用者的行为说明见 [README.md](../../README.md) 与 [configuration.md](../configuration.md) 的「工具权限」；
> 背景见 [architecture.md](../architecture.md)。只写规则与事实；推导与实测数据在对应类的注释里。

## 权限三层

**核心策略 → PLAN 只读白名单 → 插件拦截**，再统一处理 ASK 与审计。

- **fail-open 只覆盖「取不到策略」**；策略一旦生效，它的否定就是硬结论。

## 插件拦截：三态，取最严

- **`PermissionVerdict` 是三态（`ABSTAIN` / `ASK` / `DENY`）**，合并**取最严**
  （`DENY > ASK > ABSTAIN`）且 **`DENY` 短路**。
- **同为 `ASK` 时保留先到者的理由**（覆盖它只会让审计里的理由随插件顺序变化）。
- **插件抛错按 `ABSTAIN` 处理**。
- **`PermissionVerdict` 里没有 `ALLOW`，因此「插件不能放宽核心策略」是编译期约束**；
  `ASK` 只可能让调用更严——它最终仍走 `ApprovalChannel`，拿不到批准就降级为拒绝。
- **需要 `ASK` 的理由**：只有两态时「只读命令免打扰、写类命令要人看一眼」根本写不出来，用户只剩「全放行」与
  「每次都点批准」两个选择，而后者最终会退化成前者。

## 参数改写与权限的相对位置

- **参数改写（`ToolArgumentPreRequest`）排在权限判定之前**：这是防 TOCTOU 的硬要求——若排在之后，
  审批浮层上显示的是参数 A、真正执行的是参数 B，**用户批准的东西与执行的东西不是同一个**。
  排在之前则「批准的就是执行的」，审批记录、界面轨迹行、`-cli --show-tool-args` 与会话里落库的
  `toolCalls` 是同一份文本。
- **它不是一个放宽权限的入口**：改写之后照旧走核心策略、PLAN 只读白名单与插件拦截。插件本来就是同进程的
  任意代码，安全边界是「装不装这个插件」，不是「参数在第几步被看」。
- **参数改写链上的 `DENY` 不进权限审计**：`PermissionDecidedEvent` 回答的是「权限系统放没放行」，
  而那是「插件拒了这条参数」，压根没有权限结论。混进同一个事件会让权限计数失真；它表现为一条
  `terminal=REJECTED` 的工具失败结果，原因在回灌文本里。

## 审批：fail-closed

- **ASK 由 `ApprovalChannel` 收口，只有明确批准才放行**：**无审批者、超时、溢出、通道关闭、中断一律拒绝**。
- 超时来自 `permission.approvalTimeoutSeconds`（缺省 120，**每轮现读**）。
- **`Esc` 是「拒绝 + 中断回合」**，不是只拒绝。

## 只读白名单

**只读白名单 = `plugins.configurations.<pluginId>.readOnlyTools`（用户声明的工具名清单）**，由 `ReadOnlyTools` 解析，
并按其插件配置快照缓存。

- **唯一来源**：工具描述符里**没有**「只读」这个字段（`ToolDescriptor.readOnly` 已移除）。它曾经存在，且与用户配置
  取并集，于是白名单成了一个**只增不减**的集合——提供方（插件、脚本作者，MCP 那一侧甚至是不受信的外部进程）都能把
  自己的工具塞进去，而用户没有任何手段把它拿出来。现在「谁能进 PLAN」完全由用户说了算。
- **不写就等于 PLAN 下全部不可用**：PLAN 是白名单语义，集合为空时同样拒绝（属「用户已表态」而非「取不到判据」）。
  因此用 `-p --mode plan` 之前，要先在配置里列出这次任务要用的工具名。
- **拒绝文案必须点明去哪儿声明**：PLAN 拒绝的理由里带上
  `plugins.configurations.<pluginId>.readOnlyTools`。只写「仅允许只读工具」，用户不知道该改哪里——
  而这条拒绝正是他第一次遇到这个配置项的时刻。
- **白名单为空时补一条 `ConfigWarningEvent`，每种配置只发一次**：挂在「PLAN 因白名单为空而拒绝」上，
  不挂在启动上——只读白名单为空本身是合法配置（就是「一个都不许」），缺省模式也不是 PLAN，
  启动时无条件喊一次会对根本不用 PLAN 的用户造成纯噪音。去重键是白名单快照本身
  （`ReadOnlyTools` 每次重算给出新实例），因此用户改完配置仍是空集合时会再喊一次。

## 三种外壳下的审批

- **`-tui` 与 `-server` 会挂审批者**（前者独占终端的模态交互，后者走 HTTP 审批桥），
  **`-cli` 不挂**：那里没有审批者，因此「需要审批」的调用一律按拒绝处理。
- **「有没有审批者」对外只暴露静态语义**：插件看到的 `RuntimeInfo.supportsApproval()` 回答的是
  「本外壳**具备**审批通道吗」（TUI / Server 为真、CLI 为假），**不表示此刻有人在线**——
  HTTP 下那没有可靠判据（客户端可以先提交审批而不订阅事件流，也可能流断了但页面还开着）。
  插件只能据此做降级决策，不能据此做安全判定；安全边界在本节的 fail-closed，不在那个字段。

| 外壳 | 行为 |
| --- | --- |
| `-tui` | 弹出审批选择框（`↑`/`↓` 选，`Enter` 确认，`Esc` 拒绝并中断回合），批准才执行 |
| `-server` | 推 `approval_required` SSE 事件，由 `POST /approvals/{requestId}` 裁决 |
| `-cli` | 没有审批界面（也没有审批者），**一律按拒绝处理**——绝不静默放行 |

- **`ApprovalChannel` 的头槽位是每会话一个**：同一会话内仍是「一个头槽位 + FIFO 队列 + 只对头生效 + 首次结论胜出」，
  **会话之间互不排队**。改之前是全局单槽位，会话 A 的审批没答完、会话 B 的审批就排在后面——
  而审批者只看到一条，于是 B 的回合一直阻塞到超时。`resolve` 返回「是否真的落定了一条头槽位」，
  供 HTTP 层区分 404；排队中的请求裁决它等于无事发生。

## 与工具清单过滤的关系

`ToolFilter`（子代理工具清单收窄）的判据**不重写，而是复用执行期判定**：
`PermissionManager.usableTools(agentId, mode)` 内部就是 `!evaluatePolicy(...).isDenied()`。

两处各写一遍「显式拒绝 > 需审批 > 允许收窄 > PLAN 白名单」，**迟早会在某个边界上分叉**。两个推论：

- **`ASK` 不算被拒**（那个工具可用，只是要点一下批准）。
- **插件拦截不参与过滤**（它要看参数、可能问人，是「本次调用」才能回答的问题）。
