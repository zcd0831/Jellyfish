# 设计：子代理运行时 P3 —— 共享任务列表（agent 团队）

> **状态：待确认（第 7 节列出需要拍板的 5 项）。**
> 上游总纲：[`subagent-runtime.md`](subagent-runtime.md)（D2 的远景、D7/D8 的编排边界、D9 的可观测口径）；
> 前置分册：P0（原语与 governor）、[P1](subagent-runtime-p1.md)（观测与归档）、
> [P2](subagent-runtime-p2.md)（声明式编排）均已落地。
> 本文回答总纲第 13 节的开放问题 5：「任务是内核容器还是插件容器；run 间消息是否需要（以及如何收窄）权限面」。

## 1. 范围

**做**：让一次协作里的多个 run **共享同一份工作列表**——父回合写下的任务，子代理能看见、能认领、能回写结论；
用户与模型都能看到「谁在做哪一条」。

**不做**（前瞻性地划死，理由见第 3 节）：

- **run 间消息通道**：不新增「子给父发消息」「子之间互发消息」的邮寄面（D-P3-5）；
- **拉取式工作队列 / 工作窃取**：不做「子代理循环轮询直到队列空」——那是命令式编排（总纲 D7 明确不做），
  且会把「跑多久」变成不可预测；
- **任务调度语义**：内核不做优先级、依赖调度、超时重派、失败重试；
- **跨会话 / 跨进程共享**：协作空间的边界就是一个会话（一次对话），不引入外部协调服务；
- **后台子代理 / 可 resume**：沿用总纲 D9 与 P2 的不变量，一字不改。

## 2. 落地前的关键发现：容器和任务列表都已经存在，缺的是另外三样

这一节是本文的地基。P3 最容易被做成「新造一个共享容器」，但盘一遍现状会发现**容器与任务列表都已经有了**，
真正缺的是三个更靠下的东西。

### 2.1 已经有了什么

| 已有 | 事实 | 位置 |
| --- | --- | --- |
| 一个**任务列表** | `jellyfish-plugin-todo`：一个会话一个 JSON 文件、写时原子替换、读时懒加载 + 内存缓存；`TodoStatus` 有 `pending`/`in_progress`/`completed`；工具 `todo_write` 整份重写；面板、状态行、命令齐备 | `Jellyfish-Plugins/jellyfish-plugin-todo` |
| 一个**内核侧的会话级容器** | `SessionExtensionEntry`：插件往会话里挂命名空间状态（key 自动加 `pluginId` 前缀）、**随会话一起落盘**、**不进模型上下文**、**插件停止不删条目**；已有配额：每会话 64 条、单值 64 KiB、key 256 字符 | `SessionManager:105/108/111`、`PluginContextImpl:265` |
| 一份**共享给模型的现成做法** | `TodoTurnContext`：把未完成项随**本轮用户消息**送达（append-only，刻意不放进 system prompt——否则模型每勾掉一件事就要从第 0 个 token 重新计费整段历史） | `TodoTurnContext` |
| 一套**面板落位仲裁** | 插件给的是软建议；建议的区域已有别人时按 `order` 让位、溢出落到 `DOCK` | `UiPlacement` |

### 2.2 缺的是什么（三条，全部有据可查）

**（一）子代理进不了这个协作空间——身份缺失。**

插件工具看到的会话标识只有 `ToolCallRequest.getSessionId()`，而它**是调用者自己的会话**：

```
ToolExecutor:402   new ToolCallRequest(toolName, arguments, session.getSessionId(), cancellation, sink)
SubAgentLauncher:268   child = sessionManager.createEphemeral(...)   // → UUID.randomUUID()
```

于是子代理调用 `todo_write` 时（`TodoWriteTool:93` 用 `request.getSessionId()`）写到的是**它自己那一份**列表：

- 别人看不见它写了什么；
- 它自己也看不见父回合计好的计划（`TodoTurnContext` 给它送的是一份空计划）；
- 盘上还多出一个 `<子会话 id>.json`（ephemeral 会话不落盘，但这个文件会留下）。

插件手上没有别的线索：`ToolCallRequest` 只有会话标识、取消令牌、输出旁路三样，
`parentSessionId` 只存在于内核（`AgentRunRequest` 里就有），跨不过 api 边界。

**（二）并发改同一份列表会丢更新——原子性缺失。**

会话扩展条目只有 `put` / `remove` / `list`（`Session:472`、`SessionManager:451`），**没有任何条件写入**。
两个子代理并发「读出列表 → 改我要的那条 → 写回」时，后写的覆盖先写的。
而「多人抢一份工作列表」的核心操作恰恰就是这个读-改-写：**原子认领一条还没人做的任务**。

**（三）插件不知道一次协作什么时候结束——生命周期缺失。**

会话扩展条目随会话持久化、插件停止也不删（都是刻意的：那是用户会话里的数据，不是插件的私产）。
好处是稳定，代价是插件无法「一次编排结束就收摊」——今天 todo 靠「整份重写」天然规避了这个问题。

### 2.3 结论：P3 不新增容器

**任务列表就在插件里（已有先例），并发靠插件自己的锁；内核只需要把身份交出来。**
第 3 节的决策按这个结论展开，其中只有 D-P3-1 需要改内核。

## 3. 内核侧决策

### D-P3-1 身份作为「调用期设施」挂在 `ToolCallRequest` 上（**本文唯一的内核改动**）

```java
// api：ToolCallRequest 新增三个只读字段，缺省 null
String getParentSessionId();   // 派生本次调用的那个会话；根会话为 null（对齐 Session 既有语义）
String getRunId();             // 本次调用所在的 run；不在任何 run 上时为 null
String getRootRunId();         // 本次调用所在的 run 树根；不在任何 run 上时为 null
```

**为什么挂在请求上，而不是 `PluginContext` 上加一个访问器**：唯一正确的答案是**线程作用域的**——
「我此刻在为哪个 run 干活」只有在执行这次工具调用的那条线程上才有答案。
`PluginContext` 的访问器会把这个问题变成「插件自己去猜的全局问题」：面板线程、命令线程、脚本线程上
要么得到 `null`，要么得到别人的答案。而这三个字段与 `getCancellationToken()` / `getOutputSink()` 完全同类——
`ToolCallRequest` 的 javadoc 已经把它们统称为「把内核在本次调用里能提供的**调用期设施**交给工具」。

**填充点很小**：`ToolExecutor:402` 一处构造，`Session.getParentSessionId()` 拿父会话，
`RunContextHolder.current()`（core 已经在用它）拿 `runId` / `rootRunId`。

**缺省 `null`，不抛异常**：与 `CancellationToken.NONE` / `ToolOutputSink.NOOP` 同一口径。
进程级工具调用（`new ToolCallRequest(name, args)`）、外壳侧调用、旧内核装配都是 `null`，
插件因此**不需要为「内核版本旧」写分支**。

**插件侧的协作键是一行**：`parent != null ? parent : sessionId`（子 run 落在父会话上，根会话落在自己身上）。
这一行写三遍就会漂移，所以**内核应当顺手把它固化成一条约定写进文档**；
是否再给一个派生访问器（如 `getCollaborationSessionId()`），见第 7 节待确认 3。

### D-P3-2 并发原语：**本轮不加**（先用插件自己的锁）

方向上有两条路：

| 路 | 做法 | 代价 |
| --- | --- | --- |
| A | 插件自持容器（todo 的 JSON 文件 / 内存缓存），在**一把锁内**完成读-改-写 | 零内核改动；跨插件不共享（本来也不该共享） |
| B | 内核给会话扩展条目补条件写入（CAS），插件在它上面做认领重试 | api + infra 各一处改动，值为 `Map<String,Object>` 的比较语义要定义 |

**取 A。** 理由：

1. **容器的实际形态是插件自持的**（todo 的 JSON 文件已经是），内核那份 `SessionExtensionEntry` 到今天
   没有任何任务类消费方；为一个没有消费方的容器先补并发原语，是在猜未来的形状。
2. **A 的并发是正确的**：插件的 store 是单实例、方法 `synchronized`，把整个读-改-写放进同一个临界区，
   两个子代理的认领就自然串行化——不需要版本号，也不需要 CAS。这是「一个进程内持有数据」的正常做法。
3. **B 一旦做了就难改**：CAS 的比较语义（值相等 vs 版本号）、`Map` 的规范编码、失败时的返回形状，
   全都会变成第三方插件依赖的公开契约。而现在没有压力把它做对。

**记录保留项**：若将来出现「多个插件共享同一份内核容器」或「需要跨进程」，
B 才是正确的下一步，且它的形状应当是**条件写入 + 调用方重试**（而不是内核出一个 `claimTask`——
内核不该懂任务的 schema，总纲 D8）。

### D-P3-3 协作空间的边界是**会话**，不是 run 树

任务列表挂在**父会话**上（`parentSessionId`），不是 `rootRunId`。理由：

- **同一回合里的两次 `task` 是两棵独立的树**（父回合的 `parentRunId` 都是 `null`，各自成根），
  但它们是同一次协作——按树分会让「同一份工作列表」在第二次委派时突然变空；
- **跨回合延续正是团队该有的样子**：模型说「继续昨天没做完的那三条」，列表得还在；
- **零新机制**：会话级容器/文件的生命周期已经定义好了（会话删则条目删），不需要为「树结束」造信号
  （也是 2.2（三）那个缺口的答案——它不需要被填，因为边界压根不是树）。

**不做「编排结束自动清空」**：任务列表是用户与模型的资产，清空是显式动作（`team_plan` 写一份空列表，
或 `/todo clear` 这类命令）。自动清空会让「上一轮的任务去哪了」变成一个要读日志才能回答的问题。

### D-P3-4 权限面：**键由内核给，不由模型给**，因此本轮不需要新的校验

子代理会往**父会话**里写（一个不是它自己的会话）。听起来需要一个「只能写自己父会话」的守卫，
但实际风险比看上去小得多：

- 协作键来自 `ToolCallRequest.getParentSessionId()`，**模型无法指定它**（工具参数里没有这个字段）；
- 因此插件即便不校验也写不到别处去——它手上只有内核给的那一个答案。

**真正需要校验的场景现在还不存在**：插件若把会话标识交回给模型（例如让模型填一个 `session` 参数），
那才是可被诱导的写入。P3 的约定写清楚：**协作键一律从内核的调用期设施取，不接受来自模型的会话标识**。

**记录保留项**：内核侧若要做硬守卫（「来自 run 的调用只允许写它所属的父会话」），
不能落在 `PluginContextImpl`——它是 infra，而判定要读的 `RunContextHolder` 在 core，
方向相反。真要做得从 core/cli 侧注入一个判定器，属于后续项，不是本轮的必需。

### D-P3-5 run 间**不建**消息通道

远景里的「agent 团队」容易顺着推出一条「子给父汇报进度」「子之间互传发现」的消息面。**明确不做**，理由按重要性排：

1. **没有投递点**：父在 `AgentRuntime.await` 里阻塞（P2 定的阻塞等待），它没有收件箱。
   子代理「发」出去的消息，父在阻塞期间不消费、返回后也无处消费。
2. **异步投递 = 后台子代理**：唯一能往「正在跑的回合」注入东西的通道是 `PluginContext.submit(PluginAction)`，
   而 `ActionQueue` 的约束是「动作只能落进正在跑的顶层回合」。子代理在父回合返回**之后**还想投递，
   就是后台子代理——总纲明确不做，P2 也把这条不变量又验了一遍。
3. **团队真正需要的两件事已经有了**：
   - 「看得见彼此的结论」→ P2 的编排已经把上游步骤的正文拼进下游步骤的 prompt（`needs`）；
   - 「能交接工作」→ P3 的共享列表：做不完的那条留在列表里，下一个 run 看得见、能认领。
4. **将来真需要时的正确形态**：先证明共享列表不够（例如「必须通知」而不是「可以看见」），
   再在列表上做 `topic` + 轮询，而不是新开一条通道。**通道一旦存在，就再也收不回来。**

### D-P3-6 派生权限**不需要**新机制

「团队」听起来要放开「run 之间互相派生」，但这件事今天已经被两处表达完了：

- **深度**：`subAgent.maxDepth`（默认 1）。P0 已经实现了「**等待中的 run 让出并发许可**」
  （`AgentRuntime.await` 里 `permit.suspend()` / `resume()`），所以 `maxDepth ≥ 2` 的自锁死问题在 P0 就解决了，
  调大它不需要新的调度机制，只需要一条已有的回归用例护航。
- **工具清单**：`AgentDefinition` 的 javadoc 已经写明「能不能再往下委派由深度上限与该 agent 的工具清单里
  有没有 `task` 共同决定，因此不需要第二个字段」——`AgentPermissions.deniedTools: ["task"]` 就是「这个 agent 是叶子」。

因此 P3 的答案：**团队需要的是共享状态，不是新的派生通道**。一个团队里谁可以再派生，是配置问题（agent 的
工具清单），不是机制问题。

## 4. 面向模型与用户的形态（插件侧）

### 4.1 一件必须先收住的事：**团队是「父分派 + 子回写」，不是「子拉取」**

「子代理循环轮询直到队列空」这种工作窃取形态需要**循环**，而循环属于命令式编排（总纲 D7）。
P3 的形态因此固定为：

- **父回合规划**：模型一次写下这份工作列表（整份重写，与 `todo_write` 同款）；
- **父回合决定派几个**：并发度仍由内核 governor 决定；
- **子代理认领一次、做、回写**：`claim` 是**一次快照调用**——要么拿到一条，要么明确回答「当前没有可认领的」，
  **绝不等待、绝不重试轮询**。等待会让「这个 run 要跑多久」不可预测，而 P0 之后「可预测的上界」正是既有纪律。

### 4.2 任务条目（插件侧 schema，内核不认）

```json
{ "id": "t-3", "title": "核对缓存策略", "status": "claimed",
  "ownerRunId": "3f9c…", "ownerAgent": "researcher", "updatedAt": 1710000000000 }
```

`ownerRunId` 来自 `DelegationHandle.runId()`——插件在**自己 spawn 的那一刻**就知道它，
所以「谁在做」不需要任何新通道（这是 D-P3-1 的直接红利：认领时把 `getRunId()` 一起写进去）。

### 4.3 工具面（四个，插件注册）

| 工具 | 谁用 | 语义 |
| --- | --- | --- |
| `todo_write`（已有） | 父回合模型 | 整份重写这份列表（今天的语义不变） |
| `todo_claim`（新） | 子代理 | 原子认领一条（`pending` → `in_progress` + 记 owner）；没有则明确回报 |
| `todo_done`（新） | 子代理 | 把**自己认领的那条**置为 `completed` 并回写一句结论 |
| `todo_note`（可选） | 子代理 | 中途追加一句进展，供父回合与用户看见 |

**并发正确性靠插件的锁**（D-P3-2）：三个工具都改同一份列表，读-改-写必须在 store 的同一个临界区内完成。

**`todo_done` 校验归属**：只允许把它自己认领的那条标完成（`ownerRunId == getRunId()`）。
这不是安全边界（都是自己人），而是**防呆**：两个 run 同时写一条时，后到的那个应该看到「这条已被别人完成」，
而不是把它盖成自己的结论。

### 4.4 呈现

- **回合上下文**（`TodoTurnContext`，已有）：父回合每轮带着「还有哪些没完成」；子代理的 `task` prompt 由父回合
  拼装，因此**子代理要用的任务原文随 prompt 下去**，不需要额外的注入通道。
- **面板**：今天 `TodoPanel` 已经占了 `UiRegion.RIGHT`，内核的 `SubAgentPanel` **也**是 `RIGHT`——
  这两块在默认落位上是**竞争的**（谁 `order` 小谁显示，另一个落到 `DOCK`）。
  按 P2e 的教训，P3 的面板决策只有两个好答案：**在已有面板里加一列「谁在做」**，或者**合并成一块**。
  详见第 7 节待确认 1。
- **归档**：任务列表不进 run 归档（那是 run 的 transcript）；它在会话状态里，跨重启都在。

## 6. 验收

**P3a**

- 父回合里的工具调用：`getParentSessionId()` 为 `null`、`getRunId()` / `getRootRunId()` 为 `null`（不在 run 上）。
- 子 run 里的工具调用：`getParentSessionId()` 是**父会话**、`getRunId()` 是本次 run、`getRootRunId()` 是该树根。
- 进程级调用（`new ToolCallRequest(name, args)`）三个字段全 `null`，且**不抛异常**（既有调用点零改动）。
- 既有 `ToolCallRequest` 构造器与全部调用点行为不变（回归）。

**P3b**

- **并发认领不丢更新**：N 个线程同时认领 M 条任务（N > M），恰好 M 次成功、每次拿到不同的一条，
  且列表最终没有重复 owner（这是本阶段的核心用例）。
- 子代理认领后，**父回合**再读列表能看到那条已变成 `in_progress` 且带着 `ownerRunId`——即「共享」被真正证明。
- 子代理写的是**父会话**那一份：不再产生 `<子会话 id>.json`（泄漏修掉）。
- 归属防呆：`todo_done` 对别人认领的条目返回明确拒绝，且不改动列表。
- 认领不到时不等待、不重试：立即返回「当前没有可认领的任务」（用耗时上界断言）。

**P3c**

- 面板同时显示状态与负责人；无任务时不占区域。
- 父回合与子代理看到的是同一份列表（用「父写 → 子读 → 子写 → 父读」一条链断言）。

**P3d（若做）**

- 一次 workflow 跑完，任务列表里能看到每一步的 id 与认领者，且步骤失败时那条不被标成完成。

## 7. 待确认

1. **任务列表落在 todo 插件上，还是新开一个团队插件？**
   **倾向：落在 todo 上。** 理由是 2.1/4.4 两条事实：列表、存储、面板、回合上下文**都已经有了**，
   而 `RIGHT` 区域已经有两个面板在竞争（`TodoPanel` 与 `SubAgentPanel`）——再开一块面板，
   用户得在三个槽位里用 `/ui` 二选一，而这两块信息在团队干活时**同时都是想要的**。
   新增一个插件的代价不是代码，而是**又一次面板竞争**与**两份「任务」概念**（一份给人看、一份给 agent 用）。
   反方意见也摆在这里：todo 的语义是「模型给人看的计划」，团队队列的语义是「给 agent 分派的工作」，
   合并会让一个已经很清楚的用户概念变模糊——若确认要分开，则建议新插件直接复用内核的
   `SessionExtensionEntry`（不要再造一个文件存储），并把 P3 的 CAS（D-P3-2 的 B 路）一起做掉。
2. **`claim` 的形态**：一次快照调用（**推荐**，不等待、不重试）、还是「认领不到就等一会儿」
   （会把 run 时长变成不可预测，且是变相的拉取式队列）。
3. **是否再给一个派生访问器**（如 `getCollaborationSessionId()`，内核里把这个回退规则固化），
   还是只给 `getParentSessionId()` 三个原始字段、让插件各写一行回退（**倾向后者**：少一个概念，
   且回退规则写进文档三行就说清了）。
4. **P3d（编排联动）现在做还是留到 P3 收口之后**：它需要把「spec 步骤」与「任务条目」对齐，
   价值高但会引入一处跨插件耦合（workflow ↔ todo）。
5. **`AgentRunEvent` 要不要开给插件**（P1 的遗留项）：P3 的「谁在做」靠插件的 `runId` 就够，
   **推荐不做**；真要做，目的应是「面板上把 run 状态画到任务上」，而不是让插件观测生命周期。
