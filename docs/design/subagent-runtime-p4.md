# 设计：子代理运行时 P4 —— 批间编排（agent 团队形态）

> **状态：待确认（第 7 节列出需要拍板的 4 项）。**
> 上游总纲：[`subagent-runtime.md`](subagent-runtime.md)；前置分册 P0 / [P1](subagent-runtime-p1.md) /
> [P2](subagent-runtime-p2.md) / [P3](subagent-runtime-p3.md) 均已落地。
> **本文刻意不叫「团队引擎」**：它不引入任何新引擎，只回答「每一批之间，谁看什么、依据什么决定下一批、
> 什么时候停」。**P4a / P4b 详设；P4c / P4d 留待定**（见第 5 节，它们的形状依赖真跑出来的数字）。

## 1. 范围

**做**：把一个「团队」在现有机制上跑起来的**批间契约与止损**——做不了的活能落地、卡住的活不会被
反复抢走、模型知道「看清单再决定下一批」。

**不做**（每一条都有理由，见第 4 节末）：

- **租约 / 心跳 / 超时自动改派**：不做；
- **常驻调度器、后台团队**：不做（等于后台子代理，D9 已答）；
- **团队之间的消息总线**：不做（P3 的 D-P3-5 已答）；
- **跨会话 / 跨进程的团队**：不做（协作空间的边界是一个会话，P3 的 D-P3-3 已定）；
- **优先级与依赖调度**：不做——静态依赖是 spec 的 `when`，动态分工是认领，**优先级就是清单顺序**；
- **内核侧无进展检测**：不做（判据只在模型手里，见第 3 节 D-P4-5）。

## 2. 落地前的关键发现

### 2.1 三个硬事实（决定了团队长什么样）

| 事实 | 出处 | 推论 |
| --- | --- | --- |
| **一个顶层回合最多派生 `maxSpawnsPerTurn` 个子代理**（默认 **3**），分几批都一样 | `RunTree.spawnCount` 是整棵树的单调计数（`AtomicInteger`，只增不减）；树由 `ReActLooper.execute` 在**顶层回合**入口 `runContexts.open(...)` 建立 | 「一批 3 个、看结果再派 3 个」**在同一个回合里做不到**。要更多的活，只能跨回合，或调大这个键 |
| **同一回合内的所有批次共享一本账；跨回合账本重置** | 同上（token 也记在这棵树上） | 回合内多批共享预算；一条跨 5 个回合的团队任务**没有任何聚合预算**——这是唯一必须由内核解决的问题（P4d） |
| **子代理要审批会真的问到人**（有超时兜底，超时按拒绝） | `PermissionManager` 的 `ASK` 分支经 `ApprovalChannel` 提问；它是全局队列、按会话可查（`pending(sessionId)`），**不绑顶层回合** | 「团长遇到不确定就升级给人」已经有机制，不需要新东西——团队里的人机接口是现成的 |

### 2.2 三处现成的矛盾 / 缺口（都是"各自看都合理、合起来不自洽"）

1. **spec 的步数上限与 governor 的扇出上限互相不认识**：`WorkflowSpecParser.MAX_STEPS = 12`，
   而一个回合只允许派生 3 个。一份 6 步的 spec 在默认配置下**注定跑不完**，而解析期不会拒绝它
   ——插件拿不到这个配置（`PluginContext.runtimeInfo()` 只给 shell 信息：`shell` / `hasUI` /
   `supportsApproval` / `interactive`），因此它也无法在派生之前预警。
2. **额度用尽的回报没有点名配置键**：`SubAgentLauncher.limitReason` 现在是
   「本次回合已派出 N 个子代理，达到上限 M，请自己完成剩余工作」——**没有说该改哪个键**。
   这与 P0 立下的纪律（「触达预算时说明触达了哪一项以及该调哪个配置键」）不一致：读到这句话的人
   不知道该去哪里改，而它恰恰是唯一能改的一处。
3. **一次编排失败时看不出「是额度不够」**：workflow 的首行只点**第一个受影响的步骤 id**
   （`· probe-b 失败`），而真正的原因（额度用尽）散落在正文里**每一条**未执行步骤的括号里
   （`未执行：plan（本次回合已派出 3 个子代理，达到上限 3…）`）。
   6 步的 spec 因此看起来像「1 步失败 + 5 步各有各的原因」，而那 5 条其实是**同一个原因**。

### 2.3 一处需要澄清的旧表述（**代码本来就是对的**）

P3c 的分册与代码注释写的是「**一个 run 只认领一条**」。这句话**表述错了**，行为其实是对的：

```java
// TodoStore.claim：先看自己有没有「未了结」的认领
for (item : items) if (item.ownedBy(runId) && item.status() == IN_PROGRESS) return item;
// 再认领下一条无主的
for (i…) if (item.status() == PENDING && item.owner() == null) { … }
```

`todo_done` 把条目标成 `COMPLETED`（owner 保留），于是**同一次 run 的下一次 `todo_claim` 会拿到新的一条**
——「做完再领」本来就成立。真正的不变量是「**同一 run 至多一条未了结的认领**」。
这条澄清很重要，因为团队形态**正是**建立在这个行为上：worker 连着干活不需要改代码，只需要一句提示词。

## 3. 决策

### D-P4-1 团队的形状是「批间迭代」，决策者只能是模型

```
批 = 一次 spawn → await 往返（父回合阻塞等整批）
团队循环（由模型的回合驱动）:
  1. 读清单（回合上下文已经注入，见 P3）
  2. 决定：还要不要下一批？派几个？派谁？
  3. 一次性 spawn N 个（批内并发由内核 governor 决定）
  4. 等整批返回
  5. 看清单：完成了几条、还剩几条、有没有「卡住」或「认领者已结束却没标完成」的
  6. 回到 1，或收工
```

**为什么决策者只能是模型**：批间决策的输入是「中间结果」，而把中间结果映射成下一步动作就是策略；
策略按 D7 不进内核、也不写脚本。内核管批内并发，spec/清单管批内分工，模型管批间。

**这个形态的代价要写在明处**：默认配置下**一个回合最多 3 个子代理**，所以「6 件事」需要两个回合
（人在环里，或用户说一句「继续」）。想无人值守一次做完，就得调 `maxSpawnsPerTurn`——那是 P4d 的问题
（这个键到底姓「回合」还是姓「团队」）。

### D-P4-2 第四态 `blocked`：做不了的活必须能落地

**问题**：状态只有 `pending` / `in_progress` / `completed`。一条做不了的活只能停在 `pending`，
于是**下一批又会把它领走**——抢单式协作最容易烧钱的地方就是这个：每一次重试都要花掉一整轮子代理。

**做法**：`TodoStatus` 新增 `BLOCKED("blocked", "[!] ")`；`TodoItem` 新增第四个字段 `reason`
（**只在卡住时有值**，写清为什么做不了）。**名字取 `reason` 而不是 `note`**：它不是一句备注，而是「这条为什么卡住」，人要靠它决定下一步。

- **不算「已完成」，也不算「可认领」**：`X/Y 已完成` 只数 `completed`；状态行另说一句「· 卡住 1」。
- **`todo_write` 也认这个取值**：父回合重写清单时可以说「第 3 条卡在权限上，按卡住记着」。
- **注入给模型/人的块里带原因**：`[!] 核对缓存策略 —— 需要写权限，当前会话是只读`。
  理由不写出来，「卡住」与「没人做」在人看来是一样的。

### D-P4-3 `todo_release` 与 `todo_block` 分开，且**一个动词一个工具**

子代理的完整动作集是四个：**领一条 / 做完 / 我没做（放回）/ 做不了（卡住）**。

| 工具 | 语义 | owner | 谁能调用 |
| --- | --- | --- | --- |
| `todo_claim` | 领下一条（已有未了结的则返回它） | 记上自己 | 子代理 |
| `todo_done` | 做完了 | 保留（谁做的要留下来） | 认领者；无主条目谁都可以（父回合回收计划） |
| `todo_release` | 我没做，放回去 | **清掉** | 认领者自己；父回合可以放回任何一条（收拾残局） |
| `todo_block` | 做不了（要带原因） | 保留 | 认领者自己；父回合可以卡任何一条 |

**为什么「放回」与「卡住」必须是两件事**：人看到后要做的事不同——前者是「谁有空谁接」，
后者是「得有人决定换个做法」。合并成一个状态就得靠读原因文本才能分辨。

**为什么不做成「一个工具 + `status` 参数」**：`TodoStatus` 的取值已经让模型错过一次
（把 `in_progress` 写成别的词，导致整批写入被拒——那次事故写在 `TodoWriteTool` 的 javadoc 里）。
**一个动词一个工具，模型就不用在参数里填枚举值**，这是拿既有教训换来的形状。

### D-P4-4 用 `todo_release` 而不是租约 / 心跳 / 超时改派

「worker 死了留下一条 `in_progress`」是真实故障：worker 的 run 可能 `FAILED` / `TRUNCATED` /
被取消。而**这件事是可见的**——P3d 的面板已经会说「researcher（已结束）」而条目还挂在进行中。

因此处理它的正确位置是**下一批的决策者**（模型或人）：看见就放回、换个人做，而不是引入时钟。
租约需要三个新概念（续约、过期判据、改派者），而它买到的东西在这里已经买到了。

**唯一需要补的是把话说清楚**：面板上「认领者已结束而条目还在进行中」这一行（P3d 已实现，WARN 档位）
就是「这条需要你处理」的信号；P4b 的批间引导词里再补一句，模型就知道该 `todo_release` 换人。

### D-P4-5 批间引导放在两处，各管一件事

| 落点 | 通道 | 内容 |
| --- | --- | --- |
| **选型规则**（稳定、编译期固定） | `PromptContributionRequest`（`STATIC`） | 「要委派一件小事用 `task`；分工在开工前定得下来用 `workflow` 的 spec；分工要看谁快谁慢、或者活会边做边冒出来，就把它们写进待办让子代理用 `todo_claim` 认领」 |
| **当前状态 + 一句引导**（每轮新鲜） | `TurnContextRequest`（已有，随用户消息送达） | 清单块本身；有未完成项时补一句：「还有 N 条没人做；被认领的别再派一遍；**卡住的条目需要你或人决定**」；清单空时收工 |

**为什么不把状态也放进 `STATIC`**：`STATIC` 在缓存前缀里，写上「还剩 3 条」等于每勾掉一条就
作废整段历史（这条纪律 TODO 插件已经踩过并写在 `TodoTurnContext` 的 javadoc 里）。

**为什么无进展检测不做进内核**：判据是「清单没变」（模型看得见，内核看不见）。内核只有轮数 / token
这类间接信号，做了会误判，而误判的代价是「本来还在收敛的团队被砍掉」。**它在提示词里**：
「清单没有变化时不要再派同一批」。

### D-P4-6 呈现：不开第四块面板；**「花了多少」不做**

- **不开新面板**：待办面板（`RIGHT`）已经在事实上是团队视图（计划 + 谁在做），P4a 之后再加上
  「卡在哪」。内核的子代理面板（也在 `RIGHT`）讲的是 run 粒度，两者不重复，按 `order` 与 `/ui` 处理竞争。
- **「花了多少」刻意不做**：run 通知**不补发历史、且可丢**（P3b 已定），因此插件侧累加出来的 token
  必然是「本进程内观测到的部分值」——把它画在面板上，人就会拿它当账单，而账单在 `/usage` 里。
  **宁可少一行，也不要一行错的钱。**（要真做，得由内核提供「按会话聚合的 run 用量」查询，
  那是一件独立的事。）

### D-P4-7 额度用尽要能被人看见、且点名配置键

三处一起改（都属于「把话说清楚」，不改机制）：

1. `SubAgentLauncher.limitReason` 的文本补上配置键：
   「本次回合已派出 N 个子代理，达到上限 M（`subAgent.maxSpawnsPerTurn`）——要么改这个键，
   要么把剩余工作放到下一个回合」。
2. **workflow 的首行区分「额度用尽」与「这一步失败」**：一批步被拒且原因是额度时，首行直接说
   「本次回合的派生额度用尽（N/M），剩余 K 步未执行」并点名配置键，而不是只点第一个受影响步骤的 id、
   让同一个原因在正文里重复 K 遍。
3. **解析期不预判**（插件拿不到那个配置，而且同回合可能有别人也在派生，预判也会错），
   但**拒绝理由必须当场可读**——这条与 1 是一件事。

## 4. 团队循环长什么样（用默认配置算一遍账）

配置：`maxSpawnsPerTurn = 3`、`maxConcurrentRuns = 3`、`maxDepth = 1`、`maxRounds = 8`（子 run）、
`runTokenBudget = 50 万`、`treeTokenBudget = 150 万`。

**场景：6 件事，3 个 worker**

- **回合 1**（用户：「把这六件事做完」）
  - 模型 `todo_write` 写下 6 条 → 连发 3 个 `task`，prompt 都是「从共享待办认领一条并做完」；
  - 3 个 worker 并发跑，各自 `todo_claim` 领到**不同**的一条（P3c 的并发保证）；
  - 模型等到整批返回，看到清单 3/6 → 想再派**发现额度已用尽（3/3）**；
  - 回报：「还剩 3 条，下个回合我继续」。
- **回合 2**（用户：「继续」，或者模型自己在下一轮里继续）
  - 新账本 → 再派 3 个 → 清空。

**要「一次做完」的两条路**：调大 `maxSpawnsPerTurn`（代价是单个回合可能一次烧掉很多），
或者让 worker 的 prompt 写成「**把清单里能做的都做完**」——它就会在 `maxRounds = 8` 与
`runTokenBudget = 50 万` 的双保险下连着认领（这正是 2.3 节那条澄清的意义：行为本来就允许）。
**后一条更好**：它不放松任何额度，只是让每个 worker 多干几件——3 个 worker 连着认领，清单照样能被清空。

**这也是「团长」的落点**：上面的循环由**顶层回合的模型**驱动（默认形态，人在环里）。
若要把协调噪音挪出主对话，就让一个 `lead` agent 干同样的事（`maxDepth ≥ 2` + 它的工具清单里有 `task`
与待办工具）——它买到的是**隔离**，而不是新能力：它同样只能在批间行动、同样阻塞等待。

### 5.1 落地记录：P4a

| 落地项 | 形态 |
| --- | --- |
| 第四态 | `TodoStatus.BLOCKED("blocked", "[!] ")` + `TodoItem.reason`（只在卡住时有值）。`todo_write` 的名片与解析都认它（状态取值列表是**现算**的，因此加一个枚举值就自动进 schema） |
| 两个工具 | `todo_release`（清 owner、回未开始）、`todo_block`（保留 owner、写下原因）。**一个动词一个工具**：模型不在参数里填枚举值（P4a 里 `status` 那张表已经被模型写错过一次） |
| `claim` 澄清 | 代码没改（行为本来就对），改的是注释与分册表述，并补了一条回归用例把「做完再领」锁住 |
| 原因必填 | `todo_block` 的 `reason` 空白即拒；`todo_write` 的 `reason` **不校验枚举式取值**（写了就存），为它报错会把一次本来正确的整表写入整批拒掉 |
| 已完成不接受退回 | 对已完成条目 `release` / `block` 一律 `WRONG_STATE` 并说清理由——静默退回等于悄悄撤销一件做完的事 |

**实现时定下的两条细则（分册原本没说到这一层）**：

1. **「没有 run 上下文」= 协调者视角**：父回合（或外壳发起的调用）**可以放回或卡住任何一条**——
   这正是「worker 死了留下一条进行中」的解法（D-P4-4）。而**完成仍不允许父回合代签**：
   放回与卡住是清理，「做完了」是关于工作结果的声明，要么由做过的人说，要么由明确重写计划的人说
   （整表覆盖）。这条不对称是有意的，测试里锁住了。
2. **继承的黏性从「认领」扩到「认领或原因」**：父回合整表重写时，同内容条目的 owner 与 reason
   都按内容继承。原本只判 owner，于是「父回合自己卡住一条（那时没有认领者）」之后，
   原因会在下一次重写时丢掉——而原因恰恰是人做决定时唯一要看的东西。

**测试覆盖**（todo 插件 142 用例）：做完再领（回归）、卡住后不再被任何 run 认领、放回后可被别人认领、
已完成拒绝退回、父回合的清理权与「不代签完成」的不对称、原因必填与回显、父回合重写不丢原因、
两个工具的拒绝路径与子代理落在父会话上。

### 5.2 落地记录：P4b

| 落地项 | 形态 |
| --- | --- |
| 选型规则 | 新增 `TodoGuidance`（`PromptContributionRequest` + `PromptPlacement.STATIC`）：一段编译期固定的文字，点名三种编排形态（`task` / `workflow` 的 spec / 写进待办让子代理认领）。**不复述工具名片里的取值**（那属于名片，复述迟早两边矛盾） |
| 状态随回合块 | `TodoText.promptBlock` 块尾现算一句引导：还有 N 条没人做（点名 `todo_claim`）、M 条已经在做（别再派一遍）、K 条卡住了（需要你或用户决定）。**只写用得上的那几段** |
| 注入块带原因 | 卡住的行渲染成 `[!] 内容 —— 原因`（注入块与 `/todo` 的编号清单共用同一个渲染，因此不会一边有一边没有） |
| 图例条件变了 | 原来只在「有进行中项」时补图例；现在 `[~]` 与 `[!]` 两者任一出现就补（`[!]` 同样不自明） |
| 状态行 | 补 `· 卡住 N`：进度涨不上去的两种原因（还在做 / 做不了）必须分得开 |
| 面板 | 卡住的行转 ERROR 档、接上原因（超 40 字符截断）；**卡住时让位给原因而不显示认领者**——一行放不下两者，而原因决定下一步动作 |

**三处刻意的取舍**：

1. **引导语放在回合块尾而不是 `STATIC` 里**：它随状态变（「还剩 3 条」每跑完一条就变），
   进缓存前缀等于每勾掉一件事就作废整段历史——这正是 TODO 插件当年从 `PromptContributionRequest`
   搬走状态的原因，分册 D-P4-5 已把两件事分开。
2. **引导语点名工具而不是复述用法**：`todo_claim` 怎么用写在工具名片里（每轮都在模型眼前），
   这里只说「还剩几条、可以怎么办」。
3. **卡住时不显示认领者**：面板一行只有一行的宽度，而「谁卡的」是历史、「为什么卡」是决策依据。

**测试覆盖**（todo 插件 151 用例）：卡住项在图例/注入块/编号清单三处都带原因、只有卡住项时也补图例、
三种状态组合下的引导语、状态行的「进行中」与「卡住」分开计数、面板的 ERROR 档与原因截断
（含「没有第四段认领者」的断言）、选型规则的落位与「不复述 schema」。

## 6. 验收

**P4a**

- `blocked` 条目**不可被认领**、不计入「已完成」，且状态行与注入块都会单独说一句。
- **回归：做完再领**——同一个 run `claim` → `done` → 再 `claim`，第二次拿到的是**另一条**；
  而它未了结时就再 `claim`，拿到的仍是原来那条（这条用例把 2.3 节的澄清锁住）。
- `todo_release` 清掉 owner 并回到 `pending`，随后**可以被别的 run 认领**。
- 归属与 P3c 同口径：别人认领着的条目，`done` / `release` / `block` 一律拒绝并说清原因；
  父回合（无 run 上下文）可以 `release` / `block` 任何一条。
- `todo_block` 必须带非空原因；原因是空白的调用当场拒绝（回显实际值）。

**P4b**

- 选型规则只在插件启用时出现；状态引导**只在有未完成项时**出现在回合块里（清单空时不出现）。
- 「卡住」的条目在面板与注入块里都带原因，且原因过长时截断（与既有的参数回显同一口径）。
- 无待办时面板仍然返回空贡献（不占区域）——回归。

**P4c（若做）**

- 认领按调用方 agent 类型过滤：类型不匹配的条目**不会被交给调用方**，且回报里说清为什么。
- 顶层回合仍不能认领（不在任何 run 上），行为与 P3c 一致。

**P4d（若做）**

- 跨回合的团队任务有聚合预算，触达时**点名配置键**且不再派新的一批。
- 额度用尽时：`task` 的理由、workflow 的失败摘要都指向同一个键，且 workflow 说的是
  「额度用尽，剩余 K 步未执行」而不是「第一步失败了」。

## 7. 待确认

1. **`blocked` 是否要带「重试意图」**：现在它只记原因。要不要记「谁在等什么」（例如
   「等写权限」），以便下一批自动改派给有权限的 agent？（**倾向不加**：那是 P4c 的问题，
   而原因文本已经能让人做决定。）
2. **`todo_release` 的粒度**：只放回一条，还是支持「把我认领的全部放回」？
   （**倾向只放回一条**：一次一个动词，模型不容易写错；批量是父回合整表重写的事。）
3. **`maxSpawnsPerTurn` 是不是该有「团队语义」**：它现在既管「一个回合最多派几个」，
   又在事实上管「一个团队最多几个人」。要不要拆成两个键（回合上限 vs 协作空间上限）？
   （**倾向 P4d 再定**，且倾向**不拆**——先用量出来的数字说话。）
4. **`blocked` 的英文词**：`blocked` 与内核的 `AgentRunStatus.BLOCKED`（被钩子拦下）
   同词不同义。要不要换一个（如 `stuck` / `impossible`）以免读日志时混淆？
   （**倾向保留 `blocked`**：模型对这个词的先验最强，而两者的语义差异在各自语境里不会混。）
